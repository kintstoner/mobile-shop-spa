# 10. Interface texts in locale files, with react-i18next

[Español](0010-i18n.es.md)

- Status: accepted
- Date: 2026-10-28

## Context

The first version wrote every text in Spanish inside the components and the domain mapper ("Sistema operativo",
"Precio no disponible", "Principal: 13 MP"). Changing a word meant searching the code, and a second language was
impossible without touching every file.

## Options

- **Texts as constants in the code**: what there was; no translation path.
- **A small `t()` of our own over a JSON file**: about 30 lines, but plurals ("1 producto / 47 productos"),
  interpolation and language switching would be rebuilt by hand.
- **react-i18next**: the usual choice in React, with plurals through `Intl.PluralRules`, interpolation and a React
  binding; about 18 kB gzipped.

## Decision

- **react-i18next** on its own i18next instance, with `src/locales/es.json` and `en.json`. Every interface text lives
  there, nowhere else.
- **Typed keys**: the Spanish file is the reference type, so a wrong or missing key fails the build.
- **A test keeps the languages in step**: same keys in both files and no empty text.
- **The domain produces data, not text**: prices are numbers formatted per language (`170 €` / `€170`), specs carry
  an id the UI translates, cameras are `{ main, front }`, a blank option name is `null` and the UI says "Sin
  especificar" / "Not specified".
- **Initial language**: the user's earlier choice, else the browser's first supported language, else Spanish. The
  header has a native `<select>`; the choice is stored and sets `<html lang>`.
- Texts that come from the API (specs, colour names) are data and are shown as they arrive.

## Consequences

- A new language is one JSON file plus one entry in `LANGUAGES`.
- Tests read the real Spanish file, so they still check what a user reads; the test setup switches to Spanish because
  jsdom reports an English browser, and the e2e run sets `locale: 'es-ES'` for the same reason.
- The bundle grows by about 18 kB gzipped.
